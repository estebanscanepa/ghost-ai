## Current Phase

- Canvas autosave and loading — complete against `21-canvas-autosave.md`. The canvas has a durable copy for the first time: the room's graph is watched, debounced, and written to Vercel Blob at `canvas/{projectId}.json` through `PUT /api/projects/[projectId]/canvas`, and the URL it lands at goes on the project's existing `canvasJsonPath` column. An empty room is seeded back from that snapshot through the matching `GET`; a room that already has nodes or edges is never touched, so a load can never overwrite live collaboration. `types/canvas-document.ts` and `lib/canvas-document.ts` are the seam that makes it work — the stored document is the *graph* and nothing else, so selecting a node, hovering an edge, or a collaborator's cursor moving does not read as a change. `hooks/use-saved-canvas.ts` restores, `hooks/use-canvas-autosave.ts` saves, and `components/editor/canvas-save-provider.tsx` carries the status out to a new `Save` button in the navbar, which is both the indicator and the way to force a write. **The document round trip and the Blob read/write/overwrite path are verified against the real store; the editor half is not — it has still never been opened in a browser.** See Open Questions.

## Current Goal

- Persist the canvas, then generate into it. The canvas is drawable — nodes can be created, shaped, sized, named, coloured, and connected; edges route, point, and label; the viewport zooms and fits; a change can be taken back — and as of `21-canvas-autosave.md` it also survives the room. That was the last thing standing between the canvas and AI generation, which needs somewhere durable to write and a snapshot to reason about. Opening a project in a browser is still the blocking item and is now more overdue than ever: the control bar, presence, template import, and the whole save/load path are all read off the code. `LIVEBLOCKS_SECRET_KEY` and `BLOB_READ_WRITE_TOKEN` are both provisioned, so nothing about the workspace is unobservable any more — it simply has not been observed.

## Open Questions

- **Nothing has ever been saved from a browser.** The document conversion and the Blob path are verified against the real store, and the route answers unauthenticated calls correctly, but every claim about *when* a save happens is read off the code: that the debounce collapses a drag into one write, that arming makes opening a project free, that selecting a node is not a change, that a second client arriving does not restart the cycle. The arming guard in particular has no test — it depends on the live graph serializing to exactly the restored document, which is provable on paper and unobserved in practice. If it never matches, autosave silently never arms: the safe direction, but also the silent one.

- **A client can be locked out of arming by a collaborator's timing.** Exact equality against the restored document is deliberate — it is the only version of the guard where the baseline is provably what Blob holds, so autosave can never record content as stored that was not. The cost is a narrow race: if two people open the same empty room and one edits the graph in the window between the restore landing and the other's arming pass, the second client's payload never equals what it restored and it never arms for that session. Harmless as far as the data goes, because the first client is armed and is watching the same shared graph, and impossible with a single client, since nothing but its own restore touches the room. The looser alternative — arm once every restored id is present — closes the race but allows a baseline containing a collaborator's unstored node, which is the worse failure. Left as it is, on purpose, and worth revisiting if a save is ever made from outside a connected room.

- **A restore is one undo away from being erased, and then saved.** The restore is a paused-history batch, so one press of undo takes the whole thing back — and the emptied room is then a change like any other, which autosave will store over the snapshot it just loaded. This is the same shape as the existing question about undoing a template import, but with a consequence the import does not have: the import can be redone from the picker, whereas the snapshot it overwrote is gone. Options are excluding a restore from history entirely, refusing to store an empty canvas over a non-empty one, or keeping a previous snapshot. Not resolved, and not invented here.

- **The last 1200ms before leaving a project are not written to Blob.** The debounce is cancelled on unmount rather than flushed, because a flush cannot be awaited there. Nothing is lost — Liveblocks Storage has the change and the room is what the canvas opens from — so the snapshot simply lags until the next edit. It becomes real only if a room's Storage is ever cleared without the snapshot having caught up.

- **A room that predates its project's first save is only stored when someone presses `Save`.** Autosave arms on what the room already holds, so an existing project whose `canvasJsonPath` is still `null` sits unstored until its graph changes. The button covers it deliberately — `saveNow` writes whether or not anything changed — but nothing tells the user that is what needs pressing, and `Save` looks the same as it does for an already-stored canvas.

- **Concurrent saves are last-writer-wins.** Every client in a room autosaves, so two people editing at once both `PUT`, and the later request wins the blob. That is harmless while their rooms agree, which they do — Storage is the shared document and both are serializing the same graph — but nothing enforces it. `@vercel/blob` exposes `ifMatch` for exactly this, and it is unused. Worth revisiting if a save is ever made from something that is not a connected room, such as the AI generation writing a snapshot from a background task.

- **A template import has never touched a Liveblocks room.** The picker is verified in a browser and the change types are read out of `@liveblocks/react-flow`'s source, but three claims are still only claims: that `onDelete` with every node and edge empties the room, that the `add` changes then land as a complete graph, and that `fitView`'s queued latch is cleared by the template's own measurement rather than by the pre-import nodes. The last is the one with a plausible failure: if React Flow's own `requestAnimationFrame` in `BatchProvider` runs `setNodes` with the *old* nodes before the Storage write reaches React, the fit resolves against the canvas that was just cleared. **One import in the app answers all three.**
- **Import on canvas creation is not built.** `architecture-context.md` says import "can occur on canvas creation or from within the editor at any time"; only the editor path exists. `18-starter-template.md` asked for the navbar entry point and nothing else, so this is a gap in the architecture doc's coverage rather than in the spec's — it needs a spec of its own before the create dialog grows a template step.
- **A template import is one history entry; a drag may still be hundreds.** The pause/resume around the import is the same fix the open question below proposes for dragging, applied to the one action that needed it now. If the drag question turns out to need `history.pause()` on drag start, the two should end up looking the same.

- **One press of undo may take back one pixel of a drag rather than the drag.** Liveblocks groups the ops applied in a single batch into one history entry, and `@liveblocks/react-flow` does not pause, resume, or batch history anywhere — verified by grep, not assumed. React Flow dispatches a `position` change per `pointermove`, and consecutive pointermoves are separate ticks, so a node dragged across the canvas plausibly leaves one history entry per frame. If that is what happens, undo is unusable for the most common gesture on the canvas and the fix is `history.pause()` on drag start and `history.resume()` on drag stop. `17-canvas-ergonomics.md` asks only that undo and redo use Liveblocks history, which is what was built — nothing was added here on the strength of a guess. **One drag in the app answers it.**

- **Undo is per user, and the canvas is not.** Liveblocks room history is scoped to the local client, so `Cmd + Z` takes back this user's last change and never a collaborator's. That is the right default and it is also not something the UI says anywhere — two people editing the same diagram will see a redo button dim itself for reasons that are not visible on screen. Whether the control bar should say whose history it is, is a product decision the spec does not make.

- **Every selected node shows its own colour toolbar, so a multi-selection shows several.** `isVisible={selected}` is the literal reading of "only show it when the node is selected", and it is what was built. React Flow's own default — omitting `isVisible` — hides the toolbar unless the node is the *only* one selected, which would avoid a marquee selection of ten nodes floating ten pills over the canvas; it also invents a rule the spec does not state. The clutter is real and so is the misleading part: a swatch click only ever recolours its own node, so several toolbars promise a bulk edit that does not exist. The fix is deleting one prop. Whether multi-select should hide the toolbar, or recolour every selected node, is a product decision `15-nodes-color-toolbar.md` does not make.

- **Double-clicking a swatch may still zoom the canvas.** `nopan` covers pans, and it was verified against `createFilter` in `@xyflow/system` — but d3-zoom's `dblclick.zoom` is bound on the selection directly and, by the library's own comment, deliberately bypasses that filter. The toolbar portals into `.react-flow__renderer`, which is that selection, so a double-click on a 20px swatch could zoom the viewport. This is the same unresolved ordering question already recorded for the label editor's `stopPropagation`, and it is unresolved for the same reason: React dispatches from its root container, while d3's listener sits on an element *below* the root and *above* the toolbar, so which runs first is not something reading the source settles. Nothing was added here on the strength of a guess. One real double-click in the app answers it for both, and if the answer is bad the fix is a capture-phase handler, not another class.

- ~~**An edge can be created but not styled, and it is persisted that way.**~~ **Closed.** `DEFAULT_EDGE_OPTIONS` now writes `type: "canvasEdge"`, the stroke, and the arrowhead onto every new edge, which is safe precisely because the renderer landed in the same change. See Architecture Decisions.

- **A selected edge and a hovered edge look identical.** `16-edge-behavior.md` says to "brighten edges when hovered or selected" and groups the two, so one brightening serves both — which means there is no way to tell, from the edge alone, that the one under the pointer is also the one `Backspace` would delete. React Flow's `--xy-edge-stroke-selected` seam would have given selection the brand cyan for free, and it is now dead for `canvasEdge`: the stroke is an inline style on the edge record and inline wins. Recolouring on selection is not a one-line change either — `markerEnd` is a resolved `url(#…)` baked from the record, so the arrowhead cannot follow the line without a second marker, and a cyan line with a white arrowhead is worse than no cyan at all. Whether a selected edge should read differently from a hovered one is a product decision the spec does not make.

- **The label commits at the end, and a node's label commits per keystroke.** The spec asks for an edge label saved "on blur, Enter, or Escape", which is what was built — so an edge label reaches a collaborator when the editor closes, while a node label reaches them as it is typed. Two rules for two kinds of text in the same document. Neither is wrong on its own and both match their spec; nobody has decided whether they should agree. `Escape` saving rather than cancelling is part of the same literal reading — there is deliberately no third outcome hiding behind it, but it is not what `Escape` usually means.

- **A 20px band along every edge no longer pans the canvas.** `nopan` on the hit path is what stops the double-click that opens the label editor from also zooming the viewport — verified by measuring the viewport transform across a real double-click — and it necessarily takes the pan gesture with it. React Flow makes the same trade for every draggable node, where the gesture at least does something; on an edge, dragging now does nothing at all. On a canvas dense with edges that is a lot of dead surface. The alternative is a capture-phase native listener that stops the `dblclick` before d3 sees it, which is machinery for a cost nobody has felt yet.

- **`updateEdgeData` has never written into Liveblocks Storage.** The label round trip was measured end to end in the harness — double-click, type, `Enter`, badge — but the harness runs on `useEdgesState`, not on `useLiveblocksFlow`. What is unobserved is the half that matters for collaboration: a new edge has no `data` key at all (it is not in `EDGE_BASE_CONFIG`, and `DEFAULT_EDGE_OPTIONS` deliberately does not seed one), so the first label is a `replace` change that *introduces* a key onto a `LiveObject` another client is also holding. That it merges rather than clobbers is read off `@liveblocks/react-flow`'s source, not seen.

- **Nothing has actually been connected.** Handle geometry, size, colour, reveal on hover, reveal on selection, and the pointer-events toggle were all measured in a browser; the drag itself was not performed. What that leaves open: whether a drop in the middle of a large node falls outside React Flow's default 20px `connectionRadius` and silently does nothing, whether the 9px targets are comfortable at low zoom, and whether the reveal-on-hover timing feels right when crossing a dense canvas. Same blocking item as everything else — the app in front of a live room.

- **A node cannot be connected to itself, by a decision made here rather than by a spec.** `isValidConnection` rejects `source === target` because a loose-mode self-drop draws a degenerate path that reads as a bug. Retry loops and self-referential states are legitimate in some diagrams, so if one is ever wanted the fix is a self-loop edge path, not removing the guard.

- **No resize handle has been dragged and no label has been typed into.** Both states were measured statically in a browser — handles at the right size and colour, the editor pixel-aligned to the label in all six geometries — but a static render proves layout, not behaviour. What is unobserved: whether `keepAspectRatio` on the circle feels like a lock or a fight, whether 7px dots are grabbable at low zoom, whether the auto-sizing textarea grows smoothly as a label wraps to a second line, and whether `stopPropagation` on the double-click is enough to keep the viewport from zooming under a real double-click rather than a synthetic one. Every one of these needs the app open in front of a live room, which is still the blocking item below.

- **Double-clicking a rectangle's or a pill's outer margin does not open the editor.** The double-click target is the label's own box, which for those two geometries is inset by `px-3` / `px-5` — so a 12px strip down each side of a rectangle and a 20px strip on a pill is inside the node but outside the target and does nothing. The spec says to double-click "the centre/label area", and the padding is the shape's breathing room rather than label area, so this is the literal reading; the alternative is to make the whole node the target, which would also make a diamond's empty corner open its label. Left as the narrower behaviour until someone has actually missed.

- **A label longer than its shape can hold is now clipped in two ways.** The read state was already `overflow-hidden` inside a geometric inset (recorded below); the editor adds `max-h-full`, so a label that outgrows the box turns the textarea into a scroller with no indication that it did. The two behave consistently, which is the most that was in scope — but a node whose text does not fit still gives no sign of it, in either state.

- **Nothing stops a node from being resized larger than the canvas, or smaller than its label.** `NODE_MIN_SIZE` is a floor on the box and says nothing about the text inside it: a rectangle taken to 80×48 with a long label clips it, and there is no upper bound at all (`NodeResizer` defaults to `Number.MAX_VALUE`). Whether a node should refuse to shrink below its own content, or the label should shrink with the node, is a real design question that `14-node-editing.md` does not answer.

- **The ghost preview does not scale with the canvas zoom.** `setDragImage` snapshots the preview once, as the drag starts, and the browser then owns it — there is no hook to resize it mid-drag. So the ghost is always the shape's default size in CSS pixels, which matches the node exactly at zoom 1 and mispredicts it at every other zoom: at 0.5× the dropped diamond appears half the size the ghost promised. `13-node-shape.md` asks for "the same shape type and default size that will be used on drop", which is what was built, and `fitView` on an empty room leaves the zoom at 1, so a first drop into a fresh project is accurate. Closing the gap would mean abandoning the native drag image for a custom overlay tracking `dragover` — which also needs a transparent 1×1 `setDragImage` to suppress the browser's own ghost, or the user sees two. Not built: the spec says to keep this to drag preview behaviour only, and the trade is worse machinery for a case nobody has looked at yet.

- **The native drag image has never been seen.** The preconditions are measured — all six previews are in the document, painted, off-screen, translucent, and at their exact default sizes — and `setDragImage` is two guarded lines. What has not happened is a real drag: headless Chromium cannot fire the native HTML5 drag that would produce the image, so whether the browser accepts an off-screen element is confirmed only from the specification and the way this technique is used elsewhere, not from observation. The failure mode is graceful — a browser that declines falls back to its own snapshot of the dragged icon, which is exactly the behaviour this replaces — so the cost of being wrong is the nicer preview and nothing else. First real drag in a browser settles it.

- **A label longer than its shape can hold is clipped, silently.** The label layer is `overflow-hidden` inside a geometric inset, so text that does not fit is cut off with no ellipsis and no indication there is more. "Payment authorization service" fits every shape at default size, which is what was checked; a longer string in a circle (which offers a 14% inset on a 120px box) will not. Nothing can type into a node yet, so this is unreachable today — but label editing is the next unit that makes it reachable, and whether the answer is a scroll, an ellipsis, a smaller type ramp, or growing the node is a product decision `13-node-shape.md` does not make. Decide it there.

- ~~**A node can only be created by dragging, so a keyboard user cannot create one.**~~ **Answered, and half of it is built.** The panel items now activate on `Enter` and `Space`, landing the node at the centre of the pane — the placement this question proposed, reached through the same `screenToFlowPosition` the drop uses. `role="button"` is no longer a promise the panel breaks. What is still open is **touch**: HTML5 drag does not fire on a touch device, and a tap is not a keystroke, so a tap still cannot create a node. Whether the panel gains click/tap-to-add on the same path is undecided — the keyboard fix was scoped to the `role="button"` contract the markup already asserted, and click-to-add is product behaviour no spec defines.

- **A dropped node lands with its top-left at the cursor, not its centre.** The spec says to convert the screen position and "create a new node at that position", and a React Flow node's `position` is its top-left corner, so that is what was implemented literally. The consequence is that a shape appears down and to the right of where it was released, by half its size — up to 100×70 for a diamond. Centring is one subtraction (`position.x - width / 2`), but it is a behaviour choice the spec does not make, and it cannot be judged without seeing it. Revisit once a room connects. The ghost preview added by `13-node-shape.md` is anchored at `(0, 0)` for this reason — its top-left rides the cursor, so it predicts the landing box honestly instead of promising a centred drop the code does not make. If the drop is ever centred, the anchor has to move to `(width / 2, height / 2)` in the same change, or the preview starts lying.

- **Node IDs are minted client-side, so two clients could in principle collide.** `<shape>-<timestamp>-<counter>` is unique within a tab — the counter guarantees it, and 5000 IDs in one millisecond were confirmed distinct — but two collaborators dropping the same shape in the same millisecond, having each created the same number of nodes since load, would produce the same string. A colliding `add` does not create a second node: `applyNodeChanges` in `@liveblocks/react-flow` reconciles an `add` for an existing key onto the existing node, so one user's drop would silently rewrite the other's. The collision is remote and the fix is small (a per-session random prefix), but it was left out because the spec fixes the ID format and because persistence will have to think about ID stability across Blob snapshots anyway. Decide it there.

- **The room lifecycle has never run against Liveblocks.** `LIVEBLOCKS_SECRET_KEY` is provisioned — that question is closed — but a key being present is not the same as the path working: `getOrCreateRoom(room, { defaultAccesses: [] })`, `prepareSession`, `allow(room, ["*:write"])`, and the token the client receives have never been exercised, because no room has been joined. Everything asserted about them so far is read off the SDK's types and the code, not observed. The first browser open is the test, and the plausible failures are concrete: the key belonging to a different Liveblocks project than expected, `getOrCreateRoom` rejecting a 120-character room ID, or the `userInfo` shape disagreeing with `UserMeta` in `liveblocks.config.ts`.

- **A `500` from the auth endpoint shows the loading state forever, not the error fallback.** Liveblocks treats a `500` as retryable and keeps re-attempting, so `ClientSideSuspense` never resolves and never throws: the canvas sits on `Connecting to the canvas…` indefinitely. `CanvasErrorBoundary` only catches what the suspense hook actually throws, which is the non-retryable class (a `403`, a changed room ID). `11-base-canvas.md` asks for "an error fallback for Liveblocks connection issues" and an error boundary paired with `ClientSideSuspense` is what the Liveblocks docs specify for that, so that is what was built and nothing more. Closing the gap means `useErrorListener` — it reports `ROOM_CONNECTION_ERROR` with a code, including the `-1` authentication case — driving the same surface, possibly with a timeout so an endless retry eventually gives up. Not built: it is beyond the spec. The missing key used to be the guaranteed way in, and provisioning it removed that — but it did not close the gap, it only made it rarer: the endpoint still answers `500` whenever Clerk, the database, or Liveblocks itself fails, and every one of those becomes an indefinite spinner with no way out.

- **Nothing writes the canvas anywhere but Liveblocks Storage.** `Project.canvasJsonPath` exists for the Vercel Blob snapshot per `architecture-context.md`, and it is still null on every row. Storage is durable, so this is not data loss — but the storage model says canvas content belongs in Blob with the database holding the reference, and right now Liveblocks is the only copy. `11-base-canvas.md` explicitly scopes persistence out. When and what triggers a snapshot — debounced writes, on disconnect, on spec generation — is undecided.

- **`CurrentIdentity.email` is no longer dead, but only just.** Two units ago it was kept on the assumption sharing would need it, and sharing did not — the self-invite guard matches every verified address. It now has exactly one reader: the Liveblocks session label falls back to it when Clerk has no name or username set. That is a thin justification for a field on a shared identity type, and if a later unit gives the label a better fallback the case for deleting it returns.

- **Nothing evicts a stale room token.** A token is minted per join, and access is re-checked on every mint, so a removed collaborator cannot get a new one — but the one they are already holding stays valid until it expires, and a tab already inside the room keeps writing to it. This is the concrete form of the eviction gap recorded below, now that the canvas is about to become real. Liveblocks' REST API can update a room's permissions or disconnect users; whether removal should call it is undecided.

- **Cursor colours are derived, so two collaborators can share one.** Eight palette entries and a hash means a nine-person room has a guaranteed duplicate, and a five-person room has a ~50% chance of one. Deriving is what keeps a person's colour stable across rooms and devices with no coordination; assigning per room would remove collisions inside a room at the cost of that stability and of a room-level allocation protocol. Not decided — it only matters once rooms routinely hold more than a handful of people.

- **An invite is not verified against Clerk, and is not notified.** `POST .../collaborators` stores any well-formed address, whether or not a Clerk account exists for it. That is what makes an invite work before the invitee has signed up — the row waits, and `listSharedProjects` picks it up once they verify that address — but it also means a typo silently creates a collaborator nobody can use, and the dialog shows it as a bare email indistinguishably from a real user who simply has no Clerk profile yet. `09-share-dialog.md` specifies the email-only fallback and says nothing about verification or an invitation email, so neither was built. Whether an invite should be rejected when Clerk has no user, and whether it should send mail, is undecided.

- **Removing a collaborator does not evict them from an open workspace, and that is no longer cost-free.** Access is resolved server-side per request, so their next navigation is denied — but a tab already sitting on `/editor/[roomId]` holds a live room connection and keeps reading *and writing* the shared graph until its token expires. The earlier note said this cost nothing "because the canvas is a placeholder"; the placeholder is gone. Revoking the room token, or calling Liveblocks' REST API to disconnect the user on removal, is the fix and is still undecided.

- **The navbar title has a transient gap right after a project is created.** `EditorShell` resolves the open project out of the lists `app/editor/layout.tsx` fetched, and Next does not re-render a shared layout on a client navigation — so between `router.push("/editor/<id>")` and the `router.refresh()` that follows it, the new project is not in `ownedProjects` yet. For that window the navbar shows no title, no share button, and no AI toggle, and the sidebar highlights nothing. It self-heals when the refresh lands. Passing the project down from the page (which already resolved it server-side) through a context registrar would close it, at the cost of a provider and an effect. Not done — the spec is satisfied steady-state and the machinery did not look worth it yet.

- **Nothing keeps the room ID readable once names repeat.** Two projects named the same thing differ only by their suffix, and the sidebar shows names, so the ID is only visible in the Create dialog and the workspace placeholder. Whether the workspace URL should stay human-readable — or whether the suffix should grow once real users create many projects — is undecided.

- **Presence has never had two connections.** Every claim in `19-presence-avatars-cursor.md`'s unit is read off the code: that `other.id` is the Clerk user ID (it is what `prepareSession` is called with, but the round trip has not been watched), that a second face appears with the divider, that a cursor tracks a collaborator across a pan, and that `onMouseLeave` clears it rather than leaving a pointer parked at the edge. The canvas components before this one could be verified standalone; this one cannot — a room with one person in it renders exactly the empty state.

- **The avatar group clears the AI sidebar by agreement, not by measurement.** `--canvas-right-inset` is `20.75rem` because the sidebar is `w-80` at `right-3`. Change either and the two drift apart silently — the group would slide under the panel with no type error and no failing build. The alternative was a context carrying the open state into the room, which is more machinery for a value only CSS reads.

- **One person in two tabs is two faces, and the Clerk filter is exactly why.** Their own second session is excluded, so they do not see themselves — but every *other* participant is keyed by connection, so a collaborator with two tabs open appears twice in the stack and pushes a third person toward the `+N` chip. The spec asks for the presence list filtered by user ID and nothing more, so that is what was built; deduplicating by user ID is a decision that has not been made.

- **`thinking` is declared and never written.** It was `isThinking` and unused since `10-liveblocks-setup.md`; the rename keeps the key the spec names, and nothing sets it until AI generation exists. A collaborator cannot yet see that the canvas is about to change under them.

- **The AI sidebar has not been on screen.** Every canvas unit since `13-node-shape.md` was verified in a browser standalone, and this one was not: it is a client component that sits inside the editor shell, so rendering it means Clerk and a project, and the claims about it are read off the code. The specific ones worth checking first are that the transcript is the only thing that scrolls (three `min-h-0`s and a `flex-1` are what promise it), that the composer grows between 72px and 160px, and that the tab overrides actually beat the primitive's `dark:data-active:*` classes through `tailwind-merge`.
- **`field-sizing-content` is the whole of the auto-resize, and Firefox does not support it.** The `Textarea` primitive ships the property and this unit only bounded it. Where it is unsupported the composer stays at its 72px minimum and scrolls — acceptable, and the same behaviour a plain textarea has, but it is not what the spec asked for on that browser. A `scrollHeight` fallback is a ref and an effect away if it matters.
- **The transcript is component state, so it dies with the tab.** Switching to `Specs` and back unmounts the architect panel — Radix `TabsContent` does not `forceMount` — and the messages go with it. Closing the sidebar does not, because the panel is translated rather than unmounted. Nothing is persisted and nothing is shared with collaborators, which is right for a unit with no backend, and it will have to move somewhere else the moment a reply can arrive.
- **`Generate Spec` is a live button with nothing behind it.** The spec asks for the button and separately asks for the card's download to be `disabled`, so the contrast is deliberate and it was built that way — but a control that does nothing on click is a promise the panel does not keep until the generation unit lands.
- **The assistant bubble is built and unreachable.** `AiChatMessage` handles both roles because the spec specifies both, and only `user` is ever constructed: fabricating a reply would be inventing model output. It is the one piece of this unit no one can see yet.

## Architecture Decisions

- **Saving the canvas is membership-scoped, not owner-only.** Every other mutation in `app/api` is `ensureProjectOwner`; both canvas handlers are `ensureProjectViewer`. A collaborator drawing on a shared room is the entire point of a shared room, so a save they are not allowed to make is a save nobody makes on their behalf — their work would exist in Liveblocks Storage and nowhere else, and the first person to open the room into an empty Storage would restore a snapshot that never contained it. Invariant 3 is satisfied as written: auth is enforced at the boundary. What changes is which rule that boundary applies, and it applies the read rule, because the canvas is the shared thing. `architecture-context.md` records it in the auth model.

- **The canvas blob is private, not public.** The pathname is the project ID, which is also the room ID and is derived from the project's name — so a public blob would put every project's canvas behind a semi-guessable URL, and the value stored in `canvasJsonPath` would be a credential rather than a reference. `access: "private"` means the store token is required to read, that token is server-side, and `GET /api/projects/[projectId]/canvas` is the only door — which already checks membership. Verified: an anonymous fetch of a private blob URL returns `403`.

- **What is stored is the graph, not the canvas.** A React Flow node carries a good deal that is true of one client at one moment: `selected`, `dragging`, the `measured` dimensions, the `type` naming its renderer, an edge's `style` and `markerEnd`. None of it goes into the snapshot. This is not tidiness — autosave decides whether to write by comparing serializations, so any field that changes when the diagram does not would turn selecting a node into a database write, and two clients would take turns rewriting each other's identical snapshot. It also means the renderer's defaults are reapplied on load rather than frozen at save time, so a retuned arrowhead reaches saved diagrams; that is invariant 5 read in the other direction. Nodes and edges are sorted by `id` for the same reason: Liveblocks makes no promise about the order it hands them back.

- **Autosave arms rather than starts.** The first pass records what is already stored instead of storing it. Without that, every client opening a project would immediately `PUT` a snapshot identical to the one already there, and a room with five people in it would produce five of them. The consequence is the open question above: a room whose snapshot was never written stays unwritten until something changes, which is what the `Save` button is for.

- **A failed load disables saving instead of falling through.** A canvas that could not be read leaves the room empty, and an empty room autosaved over the snapshot it failed to read would destroy the diagram for real — the one genuinely unrecoverable outcome in this feature. So a read failure leaves autosave permanently unarmed for that mount, and the `Save` button re-states the error rather than writing. This is also why `readCanvasBlob` distinguishes a dangling reference from an unreadable blob: the first is honestly "nothing saved" and must not block a room forever; the second must.

- **The save status crosses the route boundary through a provider, in both directions.** Autosave has to live inside the Liveblocks room because the graph it watches is owned by `useLiveblocksFlow` there, and the button is in the navbar, which the editor layout renders. `CanvasSaveProvider` is the third crossing of this boundary and the first two-way one: status is reported up as state, and the button's request goes down through a callback the canvas registers into a ref. A ref rather than state because registration happens in an effect, and `react-hooks/set-state-in-effect` is an error in this project — which is also why every status transition is published from a timer or a promise callback, and why immediate saves are scheduled at `delay: 0` rather than called directly.

- **The canvas is keyed on the room id.** Both persistence hooks answer a question once — was this room empty, what does its snapshot already contain — and hold the answer in refs for the rest of their lives. `EditorShell` stays mounted across `/editor` navigations, so a room handed in as a changed prop would inherit the previous project's answers. Remounting is one line and removes the class of bug rather than guarding against it.

- **"Accent" in the AI sidebar is the AI accent, not the shadcn `accent` token.** `globals.css` maps `--color-accent` to `--bg-subtle`, a surface, so `bg-accent` with `text-accent` describes an element painted in the colour it sits on. `ui-context.md` documents a purpose-built pair for exactly these surfaces — `--accent-ai` for the fill, `--accent-ai-text` for text — and the navbar's Sparkles toggle already uses it, so the panel follows the palette rather than the class name. The same reading turns `text-white` into `text-copy-primary`: the styling rule bans raw colour classes, and the palette's near-white is what the spec meant.

- **Cursors are hand-rolled on Presence rather than taken from `Cursors` in `@liveblocks/react-flow`.** `19-presence-avatars-cursor.md` specifies the mechanism, not just the result: broadcast through the existing presence state, update on React Flow's `onMouseMove`, clear to `null` on mouse leave, and colour the pointer and its badge from the participant's presence colour. `cursor` was already declared in `liveblocks.config.ts` for exactly this, and owning the write means the canvas decides what coordinate space travels — flow space, the same conversion a dropped shape takes — instead of inheriting whatever the component chose. The library component stays unused; `Next Up` no longer points at it.

- **A canvas overlay learns about the editor chrome through a CSS custom property.** The presence group is inside the Liveblocks room and the AI sidebar's open state is in `EditorShell`, two sides of the layout/page boundary. Where the templates modal needed *behaviour* across that boundary and got a context, this needs one number that only CSS reads — so `<main>` sets `--canvas-right-inset` and the group inherits it. No provider, no prop threading through a Server Component, and no re-render of the room when the sidebar toggles.

- **Undo is the room's, not the canvas's.** There is no local history stack and no local copy of the graph to keep one for. Every change already goes into Liveblocks Storage through `onNodesChange` / `onEdgesChange` — the single door established by the node-editing unit — so the room's history is by construction the complete record of what happened, and a second stack could only ever be a duplicate that drifts. The consequence to know before building on it: history is scoped to the local client, so undo can never reach a collaborator's change, and grouping several writes into one undoable step is `history.pause()` / `resume()`, not something the button can decide.

- **A viewport action has one duration, wherever it is triggered from.** `CANVAS_VIEWPORT_DURATION` sits in `lib/canvas-viewport.ts` and is imported by both the control bar and the keyboard hook. It is one number in a shared module rather than a prop or a default argument because the two modules are peers — neither owns the other — and the failure it prevents is silent: a button and its shortcut animating at different speeds is felt long before it is diagnosed. Anything else that moves the camera (fitting to a selection, an AI-generated layout) is expected to read the same constant.

- **The keyboard hook takes a narrowed instance, not the canvas's instance.** `Pick<ReactFlowInstance, "zoomIn" | "zoomOut">` rather than `ReactFlowInstance<CanvasNodeType, CanvasEdgeType>`. Both zoom methods are free of the type parameters, so the narrowed form accepts any instance and keeps `hooks/` from importing the graph schema — the same seam that keeps `lib/canvas-drag.ts` honest. It is also a statement of what the hook may do: it moves the camera and calls two handlers, and it cannot reach the nodes.

- **An edge's presentation is written into the document, and its state is not.** `DEFAULT_EDGE_OPTIONS` merges into the connection before `onConnect` sees it, so `type`, the stroke, and the arrowhead land on the edge record and go to Liveblocks Storage. That was explicitly *rejected* one unit ago, on the grounds that writing `type: "canvasEdge"` into rooms with no renderer for it would leave documents full of edges nothing could draw — and the objection expired the moment the renderer existed, in this change. The reason to do it this way rather than reapply the styling at render time is invariant 5: a template import and the AI generation write edges too, and one declaration is what makes all three routes produce the same edge. Everything *transient* stays out — hover and editing are local `useState` in the renderer, because two collaborators may point at the same edge and neither should see the other's pointer arrive as a document change.

- **The label's position is asked for, never computed.** `getSmoothStepPath` returns the path and its midpoint from one call, and both are used. The midpoint of a right-angled path is a property of the routing, so computing it separately would be a second implementation of the routing that could quietly disagree with the first — the label would drift off the line for exactly the paths whose corners are interesting. Measured on the real path, at 2000 sample points: 0.00px off.

- **A node stores a palette id, and the pair is resolved at draw time.** `data.color` is `"blue"`, never `#10233D` — so a node's background and its text colour cannot come apart, the palette can be retuned without rewriting every node in every room, and there is exactly one function (`resolveNodeColor`) that turns a stored id into two hex values. It falls back to the default on a miss rather than throwing, because the id comes out of a shared document. The corollary is that colour is drawn in one component: `NodeShapeFrame` owns the fill on both rendering arms and the text colour on the label box, and everything inside that box inherits rather than declaring a colour of its own.

- **Palette hex are inline styles, not tokens, and that is not a violation of the styling rule.** `code-standards.md` bans hardcoded hex in components because the theme lives in `globals.css`; `NODE_COLORS` is different in kind — it is serialized into the canvas document, where `var(--…)` has nothing to resolve against, and Tailwind can only emit a utility for a colour it saw in the source. So node fills, label colours, and the swatches' `--swatch-accent` are inline, and anything that needs a *state* built from them (the swatch glow and ring) is a rule in `globals.css` keyed on a class and a data attribute.

- **Connection handles and resize handles are separated by position, not by mode.** There is no "resize mode" and no modifier key: the four corners resize and the four edge midpoints connect, on every node, at the same time. That is only possible because React Flow's resizer grabs from corners only, which is worth knowing before anyone adds a fifth control to a node — the edge midpoints are now spoken for.

- **Handles are mounted always and revealed with CSS.** React Flow decides what a dragged connection can reach by reading handle geometry out of the DOM, so mounting handles conditionally on hover would make a node undroppable rather than merely invisible. The visibility rule therefore lives in `globals.css` next to the rest of the React Flow theming, and `pointer-events` is toggled along with opacity so hidden handles do not sit on the canvas as invisible grab targets.

- **A node's two mutable properties take the same road into Storage as its creation did.** A resize is a `dimensions` change and a keystroke is a `replace` change, and both are dispatched through `onNodesChange` — the handler `useLiveblocksFlow` owns — rather than by writing to Storage directly. `updateNodeData` from `useReactFlow` is what makes the label half work: with the graph controlled, React Flow mutates nothing itself and dispatches the change instead. So there is one door into the document, and a node changed by a drag, by a collaborator, or by the AI arrives through it.

- **Who is editing is local; what they typed is shared.** The `editing` boolean lives in `useState` inside `CanvasNode` and never reaches the node record. Putting it in Storage would make one person opening an editor a document change everyone else receives, and would make two people editing two different labels a conflict rather than two independent acts. The text is the shared thing; the caret is not.

- **The frame owns where a label may go, and `NodeLabel` owns everything else about it.** `node-shape-frame.tsx` still answers "how much room does this geometry leave for text" and now hands that room to its children unwrapped; `node-label.tsx` answers "what is in it, and what happens when someone types". The seam is what let the editing unit land without touching a single geometry, inset, or stroke.

- **Minimum node size is schema, not component state.** `NODE_MIN_SIZE` sits in `types/canvas.ts` next to `NODE_SHAPE_SIZES` for the reason invariant 5 exists: the canvas is not the only thing that will size a node, and a template import or an AI-generated node has to respect the same floor a dragged handle does.

- **Shape geometry lives in one module, keyed by `NodeShape`.** `node-shape-frame.tsx` is the only file that knows a diamond from a cylinder, and `canvas-node.tsx` became a three-line dispatch as a result. The lookup is a `Record<NodeShape, ShapeGeometry>` rather than a `switch` or a partial map with a fallback, for the same reason `NODE_SHAPE_SIZES` is: adding a seventh shape to the schema then fails to compile until it is drawn, instead of quietly rendering as whatever the default arm was. The two-arm union is what keeps that honest — a CSS shape declares a radius, an SVG shape declares a path, and neither can be given the other's field.

- **Three shapes are CSS and three are SVG, which is the split `ui-context.md` already made.** A rounded box *is* a box, so rectangle, pill, and circle are a border plus a radius; a rhombus, a hexagon, and a cylinder are outlines and are inline SVG. Doing all six in SVG would put the trivial cases behind a path string and lose the border-radius rendering the browser already does well. Doing all six in CSS would mean `clip-path`, which clips the border away along with the corners it removes — a diamond would have no visible edge at all, and the "subtle at rest, brighter when selected" behaviour the spec asks for would have nowhere to live.

- **The SVG outlines are authored in a 100×100 box and stretched, with the stroke exempted.** `viewBox="0 0 100 100"` plus `preserveAspectRatio="none"` means one path per shape serves a node at any size, and every coordinate in the path reads as a percentage — so the geometry scales in both axes for free and nothing has to be recomputed when a node's dimensions change, which matters because resize is a later unit. The cost is that non-uniform scaling would also stretch the stroke, making a 200×140 diamond's horizontal edges 1.43× heavier than its vertical ones; `vectorEffect="non-scaling-stroke"` on each path removes exactly that, and it was confirmed by computed style at 0.6×, 1×, and 1.8× that every path still reports `1.5px`. The alternative — a viewBox matching the node's measured pixels — would need `NodeProps.width`/`height`, which are optional, and would put a fallback size in the renderer that could disagree with `NODE_SHAPE_SIZES`.

- **The label's inset is part of each shape's geometry, and it is `inset-*`, not padding.** A shape declares where text may sit because that is a fact about the shape: a rhombus offers the rectangle inscribed in it, a hexagon loses its two points, a cylinder loses its cap. The values are percentage `inset-*` utilities rather than percentage padding because CSS resolves a percentage `padding-top` against the containing block's **width** — `py-[25%]` on a 200×140 diamond applies 50px vertically, not 35px, which is not the inscribed rectangle and not what the number says. `top`/`bottom` percentages do resolve against height, so `inset-[25%]` means what it reads as.

- **The drag preview is the browser's own drag image over a real pre-rendered node, not a custom overlay.** `setDragImage` on a `NodeShapeFrame` sitting off-screen at the shape's default size satisfies every bullet in `13-node-shape.md` with no state and no event plumbing: the browser keeps it under the cursor, and it disposes of it on drop and on cancel, so "hide the preview afterwards" is not code that could be forgotten — there is nothing to hide, because the layer is never shown in the first place. The custom-overlay alternative has to track `dragover` at window level *and* still call `setDragImage` with a transparent 1×1 image to suppress the browser's own ghost, or the user sees two previews at once; that is more machinery and a worse failure mode. It also makes "the same shape type and default size that will be used on drop" literally true rather than approximately: the preview is the same component in a box sized from the same `NODE_SHAPE_SIZES` record the drag payload is built from.

- **All six previews are rendered up front, off-screen, rather than one built on demand.** `setDragImage` snapshots a live element as the drag begins, so the element has to already exist and be laid out — building one inside the `dragstart` handler has not been through layout yet, and `display: none` and `visibility: hidden` are both ignored by the browser, which leaves rendering it off-screen. Six small subtrees is the price. The layer is `fixed` rather than `absolute` so no ancestor's `overflow` can clip it, and it sits outside the `Panel` so the panel's `backdrop-filter` does not become its containing block.

- **A node is added through `onNodesChange`, not by writing to Storage.** The drop handler dispatches `[{ type: "add", item }]` into the same handler React Flow uses for every other mutation, rather than reaching for `useMutation` and touching the `LiveMap` under the `"flow"` key. That keeps one path into Storage: a drag-created node, a collaborator's node, and the node the AI generation will write all go through `applyNodeChanges`, so undo grouping, the sync config, and the internal representation are the library's business and not something this app has to mirror. It also means `CollaborativeCanvas` still holds no graph state — it holds a *gesture*, and hands the result to the hook.

- **The drag payload travels under a custom MIME type, and is validated on drop.** `application/x-ghost-ai-shape` rather than `text/plain` for two reasons. The first is discrimination: during `dragover` a browser withholds the data and exposes only `dataTransfer.types`, so the type is the *only* thing available at the moment the canvas has to decide whether to accept the drag at all — with `text/plain` the canvas would have to accept every text selection and every file dragged in from the desktop, then reject it after the drop. The second is trust: anything on the machine can put a string under any type, so `readShapeDragPayload()` narrows the parsed object instead of casting it, per the boundary rule in `code-standards.md`. A malformed payload is dropped silently rather than coerced to a rectangle — inventing a node in a document collaborators are watching is worse than doing nothing.

- **Default node sizes live in `types/canvas.ts`, not in the shape panel.** `NODE_SHAPE_SIZES` sits with `NODE_SHAPES` and `NODE_COLORS` because a node's dimensions are part of the graph, not part of the toolbar: invariant 5 requires user-created and imported content to share one schema, and a starter template or an AI-generated diagram whose rectangles were a different size than hand-drawn ones would be visibly inconsistent on the same canvas. The panel is a *consumer* of the sizes — it reads them when writing the drag payload — which is also why the size travels in the payload rather than being looked up again on drop: the panel stays the authority on what it offered.

- **The shape panel is a React Flow `Panel`, not an absolutely positioned element in the editor shell.** The toolbar belongs to the canvas, so it is mounted inside `<ReactFlow>` where the library keeps it pinned to the viewport — it does not pan or zoom with the graph, and it needs no `z-index` negotiation with the minimap or the two sidebars. Putting it in `EditorShell` would have meant a floating overlay that exists on the editor home too, where there is no canvas to drop onto.

- **The panel items are draggable `div`s, not `button`s.** WebKit does not initiate a native HTML5 drag from a `<button>` even with `draggable` set, and this is a macOS-first product where Safari is a first-class browser — a `<button>` would have made the panel inert for a real fraction of users. The items keep everything else a button has: an accessible name, a tab stop, a focus ring, and `role="button"`. They also keep keyboard activation, which a `div` has to implement by hand: an `onKeyDown` handling `Enter` and `Space` calls the same node-creation path the drop does, with the pane's centre standing in for the pointer position a keystroke does not have. `preventDefault` is what keeps `Space` from scrolling the editor, and `event.repeat` is checked because a native button does not fire while `Space` is held — here that matters more than it looks, since every node is a write to a document collaborators are watching.

- **`ReactFlowProvider` is mounted inside `ClientSideSuspense`, above the canvas.** `screenToFlowPosition` is the only correct way to turn a pointer position into canvas coordinates — it accounts for pan, zoom, and the pane's offset in the page — and `useReactFlow()` needs React Flow's context, which `<ReactFlow>` itself provides only to its children. So the provider has to sit a level above the component that renders it. It goes inside the suspense boundary because it is the canvas that needs it, not the loading fallback.

- ~~**The node renderer is a placeholder, and says so.**~~ **Superseded by `13-node-shape.md`** — `data.shape` is now drawn, and `canvas-node.tsx` delegates every geometry to `NodeShapeFrame`. Only the colour half of this decision still stands: the renderer is styled with surface tokens rather than `NODE_COLORS` so the palette work has one source of node colour to replace. The original entry, for the record: `canvas-node.tsx` receives `data.shape` and `data.color` and draws neither, which is exactly what `12-shape-panel.md` asks for ("render every shape as a simple bordered rectangle… shape-specific visuals will be added later"). It is styled with tokens rather than with `NODE_COLORS` so the placeholder does not become a second, competing source of node colour that the palette work then has to unpick. Its box is sized by `h-full w-full` against the node's own `width` / `height`, which React Flow applies as inline styles — so the proportions come from `NODE_SHAPE_SIZES` and the renderer has no dimensions of its own to keep in sync.

- **The Liveblocks providers are mounted in the workspace route, not in `EditorShell`.** A room ID is a URL segment, so the room's lifetime should be the route's lifetime: navigating between projects has to leave the previous room and join the next one. `EditorShell` outlives every route below it, so a provider mounted there would keep one room alive across every project and would need the room ID passed down from a page it sits above. This is the opposite trade-off from the share dialog, which *is* owned by the shell — that state is about the app's chrome, this is about the document.

- **The canvas page stays a Server Component; `CanvasRoom` is the client boundary.** Per invariant 4, `"use client"` goes at the narrowest point that needs it. Access is resolved on the server before anything renders, so an unauthorized caller never downloads the canvas at all — and access is then settled a second time by `POST /api/liveblocks-auth` before a token is issued. Two checks, deliberately: the page decides what to render, the endpoint decides what to sign.

- **The error boundary is hand-written and wraps `RoomProvider` rather than sitting inside it.** The Liveblocks docs pair `ClientSideSuspense` with `react-error-boundary` *inside* the room. Both halves were changed. It is written locally because an error boundary has to be a class component whatever the source, this is the app's only one, and thirty lines is not worth a production dependency plus an audit-gate surface. And it wraps the provider because the provider owns the connection: `Try again` keys the subtree on an attempt counter, so remounting it re-runs the auth call and dials again, whereas retrying from inside would have remounted the canvas against the same dead room and immediately re-suspended. Errors from the subtree bubble to it either way, so nothing is lost by hoisting it.

- **A node stores a palette *id*, not a colour.** `ui-context.md` defines the canvas palette as eight fill/text *pairs* — the vivid text colour is what makes the dark fill legible, so the two are meaningless apart and a single `color` field cannot hold both. `CanvasNodeData.color` is therefore a `NodeColorId` that indexes `NODE_COLORS`. The id is also what makes the palette retunable: adjusting a fill is a one-line change here rather than a rewrite of every node in every room, which matters because these values are serialized into the canvas document and into Blob snapshots later.

- **There is one node type; the shape is data.** Every node is a `canvasNode` and every edge a `canvasEdge`, with `data.shape` choosing between the six shapes rather than six React Flow types choosing between six components. One type means one renderer, one Storage shape, and one thing to migrate — and it is what lets a user change a rectangle into a cylinder by editing a field instead of replacing the node. `11-base-canvas.md` names exactly these two type strings.

- **`CanvasNodeData` is a `type` alias, not an `interface`, against the project's usual rule.** `code-standards.md` prefers `interface` for object contracts, but React Flow constrains node and edge data to `Record<string, unknown>`, and TypeScript only gives an *implicit index signature* to type aliases — an interface can be augmented, so it never satisfies that constraint. `Node<CanvasNodeData, "canvasNode">` does not compile with an interface. The reason is recorded at the declaration so it is not "corrected" later.

- **React Flow is themed by overriding its own `--xy-*` variables in `globals.css`, at three classes of specificity.** The library ships light defaults *and* a `.react-flow.dark` block of its own greys — its dark canvas is `#141414` where `--bg-base` is `#080809` — so `colorMode="dark"` alone leaves the canvas visibly off-palette. Overriding its variables is the library's documented theming seam and keeps hex values out of the component, consistent with the existing token-driven decision. The selector is `.react-flow.dark.canvas-surface` rather than `.react-flow.dark` on purpose: React Flow's stylesheet is imported from a component while this block ships with `globals.css`, and the emitted CSS confirms the two rules land in **separate chunks** — so equal specificity would have made the winner depend on chunk load order. Three classes beats two unconditionally. The translucent minimap mask uses `color-mix(in srgb, var(--bg-base) 65%, transparent)` rather than a new token, and lightningcss emits an opaque `var(--bg-base)` fallback behind an `@supports` guard.

- **The canvas is themed only as far as it renders.** Background, dot pattern, and minimap are re-pointed at the palette; edge and handle colours are left on React Flow's dark defaults. `ui-context.md` specifies those (a `#f8fafc` smooth-step arrow edge, hover-revealed white handles), but they describe the custom renderers `11-base-canvas.md` explicitly defers — encoding them now would mean hardcoded hex in a theme block for components that do not exist. Node appearance is no longer part of this: `13-node-shape.md` put it in `NodeShapeFrame` on the project's own tokens rather than in the `--xy-*` block, because a node is this app's component and not React Flow's chrome.

- **The minimap sits bottom-left.** React Flow defaults to bottom-right, which is exactly where `AiSidebar` is — and that panel starts *open*, so the default would put the minimap under it on every project open. The project sidebar can cover bottom-left too, but it starts closed and is a navigator users open deliberately.

- **Canvas components live in `components/canvas/`, not `components/editor/`.** `components/editor/` is the workspace chrome — navbar, sidebars, dialogs. The canvas is the document that chrome surrounds, and it is about to grow six shape renderers, an edge, controls, and cursors. Splitting it out now keeps the editor folder from becoming the place everything goes; `architecture-context.md` already lists "canvas surfaces" as a distinct concern.

- **Liveblocks is authenticated with access tokens, not ID tokens.** ID tokens are Liveblocks' recommended method, and they were rejected on purpose: they decide permission from the room's own `usersAccesses` / `groupsAccesses`, which would mean mirroring `ProjectCollaborator` into Liveblocks and keeping the two in sync on every invite and removal. Membership here is keyed by *email* and resolved through the caller's verified Clerk addresses, which does not map onto a Liveblocks user ID ACL at all — an invite to someone who has not signed up yet has no user ID to grant. An access token instead carries the grant the server just derived, so the database stays the single source of truth and a removed collaborator stops being issued tokens on their next join. The room is still created with `defaultAccesses: []`, so it is private and unreachable except through a session this endpoint authorized.

- **The room is created lazily, by the auth endpoint.** `getOrCreateRoom` runs on every join, which makes "does the room exist" a question nobody has to track: it is idempotent, the project record is the source of truth, and creating the room at project-creation time would put a second network call on the create path and leave an orphaned room behind whenever the project insert failed after it. The cost is one extra Liveblocks call per join.

- **The Liveblocks auth route answers `403` for a room that does not exist.** It uses `checkProjectAccess`, the workspace route's helper, not the API's `ensureProjectViewer` — so "gone" and "not yours" collapse into one answer. The rest of `app/api` keeps them apart because a UI needs to tell a deleted project from a forbidden one; this endpoint has no such caller. Its only client is the Liveblocks provider, which does the same thing either way, and a distinct `404` would let anyone probe which room IDs are real.

- **The Liveblocks client is built on first use; Prisma's is built at import.** `lib/prisma.ts` constructs at module load and throws without `DATABASE_URL`, which is right because nothing in the app works without a database. `LIVEBLOCKS_SECRET_KEY` is needed by exactly one route, and `next build` imports every route module to collect page data — so a module-level throw would turn a missing key into a failed build rather than a failed room join. The caching is otherwise identical: a module-level variable, plus `globalThis` outside production so hot reloads reuse the instance.

- **Cursor colour is derived from the user ID, not stored.** FNV-1a over the ID, modulo an eight-colour palette. Deterministic means the same person is the same colour in every room, on every device, and across reconnects, with no column to migrate and no allocation to coordinate between clients. The palette is the canvas node *text* colours from `ui-context.md` rather than the surface tokens: those are already tuned to read against the near-black canvas, which is exactly the constraint a cursor has. They are hex literals rather than CSS custom properties because the value is serialized into a token and rendered as an SVG fill, where `var(--…)` has nothing to resolve against.

- **Presence carries a nullable cursor.** `cursor: { x, y } | null` rather than an always-present point: a pointer that has left the canvas has no position, and the alternative — leaving the last coordinates in place — renders a cursor for someone who is not there. `isThinking` sits alongside it rather than in Storage because it describes the *user*, not the document, and should disappear with them when they disconnect.

- **Collaborator emails are lowercased on both sides of the comparison.** `ProjectCollaborator.email` is matched against the caller's Clerk addresses with a plain SQL `in`, which is case-sensitive, so an invite to `Ada@Example.com` would never match the account that owns it. `normalizeCollaboratorEmail()` lowercases on the way in and `getCurrentIdentity()` lowercases on the way out. Normalizing beats Prisma's `mode: "insensitive"` here because it keeps the `email` index usable and puts one canonical form in the column.

- **Reading the collaborator list is owner-or-collaborator; changing it is owner-only.** A collaborator can see who else has access — that is the read-only half of the share dialog, and it is information they already have by being in the project. Invite and remove go through `ensureProjectOwner`, per invariant 3. `canManage` in the dialog is the same kind of affordance as the sidebar's rename/delete: presentation, re-checked at the boundary.

- **`ensureProjectViewer` distinguishes 403 from 404; `checkProjectAccess` does not.** The same rule, two callers with different obligations. The workspace *page* collapses "gone" and "not yours" into one `AccessDenied`, because a distinct message would tell an outsider which room IDs are real. An API *handler* keeps them apart, because the rest of `app/api` does and because the share dialog is only ever opened from a project the caller can already see. The existence query that separates the two runs only after access was refused, so the allowed path pays nothing for it.

- **Clerk is the user directory; there is still no local user table.** `ProjectCollaborator` stores an address and nothing else, and the name and avatar are read from Clerk's Backend API per request. That is what lets an invite be sent to someone who has not signed up yet — the row waits for them. The cost is a Clerk round trip on every list read; the alternative, mirroring Clerk users locally, would need webhook sync and could go stale, which is worse for a list this small.

- **Clerk enrichment fails open.** `findClerkProfilesByEmail()` catches, logs, and returns whatever it resolved. A name and an avatar are decoration, so a Clerk outage degrades the dialog to email-only rather than turning the collaborator list into a 500. Nothing about who may see or do what is decided there — the enrichment never touches authorization.

- **The enriched profile is matched back through the user's own verified addresses.** Clerk's `emailAddress` filter is matched *back* rather than trusted positionally, and only `verification.status === "verified"` addresses are honoured. Both halves matter: the first means a change in Clerk's filter semantics cannot pair a name with the wrong address, and the second means adding someone else's address to your account unverified cannot lend you their name in a list.

- **The share dialog is not in `ProjectDialogsProvider`.** The project dialogs need a context because their two entry points sit on opposite sides of the route boundary. The share dialog has one entry point — the navbar — and acts on the open project rather than a row the user picked, so `EditorShell` owns the controller directly. Adding it to the provider would buy nothing and widen a shared context.

- **The collaborator list is fetched when the dialog opens, not server-rendered.** It is dialog-local data that only matters once someone asks for it, so the initial page load still fetches nothing on the client — the rule the project lists follow is about *page* data. The fetch hangs off the open handler rather than an effect, which is both what React recommends for a user event and what the `react-hooks/set-state-in-effect` rule enforces; a `loadId` ref supplies the staleness guard an effect's cleanup would have.

- **Share dialog state is reset during render when the project changes, not in an effect.** The hook is called in `EditorShell`, which outlives any single room, and the dialog only unmounts when there is no active project at all — so a dialog opened for one project would otherwise reappear over the next one, titled with the new project's name and listing the previous project's collaborators, since `open()` is the only path that loads data. Back/forward and the `router.replace("/editor")` that follows deleting the open project both reach it. The reset is the compare-and-adjust-during-render pattern rather than a `useEffect`: it runs in the render that first sees the new project, so there is no painted frame where the title and the list disagree, whereas an effect fires *after* that frame and would show the bug briefly. It also could not be an effect at all — `react-hooks/set-state-in-effect` is an error in this repo.

- **Every request that writes back into the dialog checks the session it belongs to.** `sessionId` is bumped by `open()` and `close()`, and the load, the invite, and the removal each capture it and bail if it has moved. The load guard alone was not enough: `invite()` appends to whichever list is current, so an invite still in flight when the room changed would have landed the new collaborator in the *next* project's list. The server-side effect of a discarded request still stands — it was addressed to the right project — only the local echo of it is dropped, and the next `open()` refetches the truth. `isInviting` and `removingId` are therefore reset by `open()` too, since a discarded callback never reaches the line that would have cleared them.

- **Invite and remove patch the local list; they do not `router.refresh()`.** Unlike create/rename/delete, sharing changes nothing the server rendered for the *caller* — their own owned and shared lists are identical before and after. The invitee's `Shared` tab is server-rendered on their next request. Refreshing here would re-fetch the whole tree to update a list the client already holds the authoritative answer for.

- **Clerk avatars render through a plain `<img>`.** They come from Clerk's own CDN, and a user with no upload gets a generated URL. Routing a 32px image through `next/image` would mean allow-listing a third-party host in `next.config.ts` and paying an optimizer round trip, and a host that turns out to be wrong would break the avatar rather than degrade it. The `@next/next/no-img-element` rule is disabled on that one line with the reason recorded in the component.

- **Prisma error codes and the browser transport each live in one module.** `lib/prisma-errors.ts` and `lib/api-client.ts` were both extracted rather than written fresh: the P2025 helper already existed in two copies under `app/api/projects/`, and the error-envelope guard would have become a second copy the moment `lib/collaborator-requests.ts` existed. A route now says `isForeignKeyViolation(error)` and a request module says `requestJson(url, init)`, and the mapping from a driver code or an HTTP envelope to a user-facing answer is defined once.

- **The workspace route denies with a rendered surface, not `notFound()`.** `/editor/[roomId]` returns `AccessDenied` for a project that does not exist *and* for one the caller may not open. Both answers are identical on purpose — a "no such project" message would tell an outsider which room IDs are real — and rendering inside the editor shell keeps the navbar and project sidebar available, so the way out is one click instead of the browser's back button. The API keeps its `403`/`404` distinction; a page has no error envelope to carry it.

- **The route segment is `[roomId]`.** Renamed from `[projectId]` per the spec. The two names describe the same string — the project ID *is* the room ID — but the URL is the room the canvas joins, so the segment says so. `useParams().roomId` is what `use-project-actions.ts` reads to detect the open workspace. The API route stays `[projectId]`: it addresses the record, not the room.

- **Identity and access live in `lib/project-access.ts`; `lib/projects.ts` keeps the project queries.** The page reads one identity and asks one question of it. `findAccessibleProject` moved out of `lib/projects.ts` to become `checkProjectAccess`, and `lib/current-user.ts` was folded into `getCurrentIdentity()` and deleted — one Clerk read now produces the user ID and the addresses together, so the layout and the workspace route cannot resolve identity two different ways.

- **The identity carries the primary address but access matches every verified one.** `08-editor-workspace-shell.md` describes the identity helper as `userId` + primary email; `architecture-context.md` resolves collaborator access through the caller's verified *addresses*. Both are kept: `CurrentIdentity.email` is the primary address, `CurrentIdentity.emails` is every verified one, and the collaborator check matches on `emails`. Matching on the primary alone would break the system against itself — `listSharedProjects` lists by every verified address, so the `Shared` tab would show a project the workspace then refuses to open. An invite sent to a secondary verified address is still an invite to that person.

- **The navbar title comes from the layout's lists, not a second query.** `EditorShell` resolves the open project by matching `useParams().roomId` against the owned and shared lists the layout already fetched for the sidebar. A project the caller can open is in one of those two lists by definition, so the title, the sidebar highlight, and the access check cannot disagree — and a project name costs no extra round trip. A miss means the editor home or a denied room, and the navbar then renders no title and no project actions.

- **The project ID is the Liveblocks room ID.** Creating a project builds `slugified-name-<suffix>` in the dialog, previews it, and sends it as the project ID; `POST /api/projects` validates the shape and stores it as the primary key. One identifier means a project record always addresses its room and a room always names its project — no mapping table, no second column to keep in sync, and the workspace URL is the room. The cost is that the client proposes an identifier, which is why the server re-validates the format and lets the primary key reject duplicates rather than trusting the string.

- **The room suffix is sized so a `409` is unreachable, not merely recoverable.** The suffix is six CSPRNG bytes (48 bits, twelve hex characters), widened from three. It only has to separate projects that slugify to the *same* name, so the birthday bound is what matters: at 24 bits two such projects collided with ~50% probability after about 4.8k of them, which put a duplicate-ID `409` on the routine path. That mattered because recovery is not automatic — `POST /api/projects` answers `409`, and `use-project-actions.ts` rolls a fresh suffix and renders the error, but the user has to submit again. Adding an automatic resubmit would have hidden a collision rate that should not exist; 48 bits moves the 50% point to ~19.7M same-named projects instead. Widening was migration-free because `isRoomId` checks shape and a maximum length and never the suffix's length, so IDs already issued at six characters stay valid, and `buildRoomId` reserves space from `suffix.length` rather than a constant, so the 120-character cap adjusted itself.

- **The `slug` field is gone; the room ID replaced it.** `Project.slug` existed only to preview the URL a name would produce, and that preview is now the room ID. Nothing derives, stores, or routes on a separate slug, which closes the question `06-project-apis.md` left open — no `slug` migration was needed.

- **Both project lists are fetched in the route layout, not the page.** The sidebar lives in `app/editor/layout.tsx`, so that is the closest Server Component that can hand it data. Fetching in `app/editor/page.tsx` would leave the workspace route's sidebar empty and force a second query per screen. This is what makes `/editor` a dynamic route.

- **Mutations reconcile through `router.refresh()`, not local state.** The lists are server-rendered, so the client does not hold a copy to patch. A successful create, rename, or delete asks the server for the tree again, which keeps one source of truth and means a change made in another tab shows up on the next mutation. Create additionally pushes to the new workspace; deleting the workspace that is currently open replaces the route with `/editor` rather than leaving a dead URL rendered.

- **Read access is owner-or-collaborator; mutation stays owner-only.** `checkProjectAccess` gates the workspace route on either, per the auth model. `ensureProjectOwner` still gates rename and delete. A project the caller may not read renders `AccessDenied` from the workspace route — not the API's `403`, because a page has no error envelope to distinguish "not yours" from "gone", and the sidebar only links what the user can already see.

- **Collaborator lookup uses verified emails only.** `ProjectCollaborator` is keyed by email, so `getCurrentIdentity()` resolves the caller's addresses from Clerk — filtered to `verification.status === "verified"`. An unverified address is an unproven claim; matching on it would turn "add an email to your account" into "join someone else's project".

- **A failed mutation keeps the dialog open.** Every request resolves to `{ ok }` rather than throwing, and the message from the API's `{ error: { code, message } }` envelope renders inside the dialog. `code` is carried through as well, so the one failure the client can act on — a `409` on a taken room ID — rolls a fresh suffix instead of retrying the same one.

- **Routes are protected by default; the public list comes from the env vars.** `proxy.ts` calls `auth.protect()` on every request that is not sign-in or sign-up, so a new route is private the moment it exists — forgetting a guard fails closed. The public matcher is derived from `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` rather than hardcoded, so the public surface and Clerk's own redirect targets cannot drift apart. This is coarse gate-keeping only: per-project ownership checks still belong at each mutation boundary.
- **The API surface is gated in `proxy.ts` by an explicit check, not by `auth.protect()`.** `auth.protect()` answers an unauthenticated request with a redirect for document requests and a **404** for everything else — a `fetch` to `/api/projects` would never see a `401`. So `proxy.ts` matches `/api(.*)` separately, reads `userId`, and returns the same `401` envelope the handlers use. The default is unchanged — anything not public and not API still goes through `auth.protect()`, so a new page route is private the moment it exists — and each handler re-checks `userId` itself, so the route is closed even if the matcher is ever wrong.

- **Handlers own the HTTP boundary; `lib/projects.ts` owns the rules.** A route handler reads the session, parses the body, calls one domain function per concern, and returns. Validation, the default name, the owner check, and the wire shape all live in `lib/`, so the create and rename paths cannot drift apart and none of it has to be re-tested through HTTP.

- **404 and 403 are distinguished on purpose.** A mutation against a project owned by someone else returns `403`, not a `404` that would hide its existence. `06-project-apis.md` requires it, and the sidebar only ever renders rename/delete for projects the user can already see.

- **`/` is a router, not a page.** There is no marketing surface at the root — it reads the session and redirects to `/editor` or `/sign-in`. Anything public-facing would need its own route added to the public matcher.
- **Clerk is themed by variable, not by element.** `appearance` uses Clerk's `dark` theme as the base and overrides its `variables` with the project's CSS custom properties. Nothing targets Clerk's `elements` classes, so restyling Clerk means changing a token in `globals.css` and Clerk internals stay upgradeable.

- **The route layout stays a Server Component; the shared state lives one level down.** `isSidebarOpen` is shared between the navbar toggle and the sidebar, so it has to sit above both — but putting `"use client"` on `app/editor/layout.tsx` would drag every future editor screen's chrome onto the client boundary for no reason. `EditorShell` absorbs the client-ness instead, and `children` still arrives from the server untouched.

- **The two sidebars have opposite defaults.** `ProjectSidebar` starts closed — it is a navigator you reach for between projects. `AiSidebar` starts open, because the AI panel is a standing part of the workspace rather than a detour, and a placeholder nobody can see is a placeholder nobody reviews. Both are overlays either way, so neither default changes the canvas viewport.

- **The sidebar overlays, it never reflows.** `ProjectSidebar` is absolutely positioned and stays mounted in both states — closed just translates it off the left edge (plus `inert` so it drops out of the tab order). Any screen that renders it must supply a `relative` container. This keeps the canvas viewport size constant, which matters once React Flow owns that area.
- **Dialogs compose `EditorDialog`, not the shadcn `Dialog` directly.** The overlay, radius, surface, and footer treatment live in one place; concrete dialogs supply only title, description, body, and footer actions.

- **Project dialog state is one controller shared through context.** The two entry points sit on opposite sides of the route boundary — the sidebar is in the layout, the `New Project` button is in the page — so neither can pass props to the other. `ProjectDialogsProvider` (mounted in `EditorShell`) holds the single `useProjectDialogs()` controller and renders the dialogs once; anything below reaches it through `useProjectDialogActions()`. Only one dialog is open at a time, so one `kind` plus one name field is the entire state.

- **Dialog components are presentational; the hook owns the state.** Each dialog takes `open`, its field values, and callbacks — no dialog holds its own `useState`. When persistence lands, the mutation goes into the hook's `submit()` and no dialog component changes.

- **The name is validated by the slug it produces.** `name.trim().length > 0` is not enough — `"!!!"`, `"---"`, and `"@#$"` all pass it and slugify to `""`, which would create a project with no slug. `canSubmit` requires a non-empty slug for both create and rename, so a name that cannot address a project cannot be submitted. This is a UX guard, not the authority: the server has to re-derive and enforce the slug (plus uniqueness) when persistence lands.

- **The identifier is shown at creation, not in the lists.** The Create Project dialog previews the room ID the name will produce, because that is the moment the user still controls it. Sidebar rows — owned and shared alike — show the project name only; the identifier is a URL detail that adds noise to a list. Routing uses `Project.id`, which is the room ID; there is no `slug` field on the model.

- **Ownership is a UI affordance in the sidebar, not an authorization check.** Rename and delete render only for `ownership === "owned"`, which is presentation. The real check stays at each mutation boundary per the invariants in `architecture-context.md`.

- **The schema is multi-file; models live in `prisma/models/`.** `prisma.config.ts` sets `schema` to the `prisma/` folder rather than a single file, so `schema.prisma` holds only the generator and datasource and every domain gets its own `.prisma` file. Adding the spec, task-run, and canvas models later means adding files, not growing one.
- **The connection strategy is chosen from the URL scheme, not from an env flag.** `lib/prisma.ts` reads `DATABASE_URL` and picks Accelerate for `prisma+postgres://` or the `@prisma/adapter-pg` driver adapter for everything else. Prisma 7 requires one or the other — there is no engine-managed default — and deriving it from the scheme means moving between a direct Postgres URL and an Accelerate URL is a `.env` change with no code change. 
- **The TLS policy lives in `lib/database-url.ts` and gates the CLI as well as the app.** `assertVerifiedDatabaseUrl()` was extracted from `lib/prisma.ts` and is now called from `prisma.config.ts` too. The app was the only thing enforcing it before, which left the larger hole: `prisma migrate deploy`, `db execute`, and `studio` open their own connections from the raw `DATABASE_URL`, so a migration could have been applied over an unverified connection to a database the app would then refuse to open. The module imports nothing and reads no environment, because `prisma.config.ts` is loaded by the Prisma CLI's own TypeScript loader — outside Next's module graph and without its path aliases, so it imports the helper by relative path and anything the helper pulled in would have to resolve there too. `lib/prisma.ts` now calls it before the Accelerate branch rather than inside the `pg` one: the helper owns every exception, so neither consumer has to know what they are.
  - Two consequences worth knowing. The helper treats an unset or empty URL as "nothing to check", because `prisma generate` and `prisma validate` legitimately run without a database and a fresh clone's generate step must not fail — "is it set" stays in `lib/prisma.ts`, which cannot build a client without one. And because the check runs when the config module loads, it gates *every* Prisma command, including ones that never dial: with a non-compliant remote `DATABASE_URL` in the environment, `prisma generate` now exits 1 where it previously succeeded. That is stricter than strictly necessary and is accepted deliberately — config load is the only hook available, and a misconfigured URL is worth fixing rather than tolerating.

- **`DATABASE_URL` is declared in `.env` only, and must be `sslmode=verify-full`.** It used to sit in both `.env` and `.env.local` as the same value, which is a drift trap: Next.js prefers `.env.local` while `prisma.config.ts` reads `.env` through `dotenv/config`, so the app and `prisma migrate` can silently diverge onto different databases. `.env` is the one file both consumers read, so the duplicate was removed from `.env.local` and replaced with a comment saying why. The `verify-full` half is a security constraint, not style: Prisma Console emits `?sslmode=require`, which `pg` currently aliases to `verify-full` while emitting a one-shot process warning, and which under pg v9 will adopt libpq semantics with no certificate or hostname verification. `.env.example` is checked in (via a `!.env.example` negation, since `.gitignore` blanket-ignores `.env*`) so the requirement is discoverable before someone pastes a Console URL.

- **Theming is token-driven, not component-driven.** `components/ui/*` stays exactly as generated; the dark look comes from `app/globals.css` mapping shadcn's semantic tokens (`--background`, `--card`, `--primary`, `--border`, `--input`, `--ring`, …) onto the palette in `context/ui-context.md`. Restyling means changing a token, not editing a foundation component.
- **Dark-only with no light palette.** The dark values live directly on `:root` (plus `color-scheme: dark`); there is no light block and no `prefers-color-scheme` branch, so the system theme cannot leak through. The `dark` class on `<html>` exists only to activate the `dark:` variants baked into the generated components.
- **`bg-base` is an `@utility`, not a `--color-base` theme token.** A `base` entry in Tailwind's color namespace also generates a `text-base` color utility, which shadows the built-in `text-base` font size and silently recolored `CardTitle`. Avoid color token names that collide with built-in utility names (`base`, `sm`, `lg`, …).
- **Radius scale comes from shadcn's `--radius` ladder** (`--radius: 0.625rem`, `xl`/`2xl`/`3xl` at 1.4/1.8/2.2×). The generated components hardcode `rounded-xl`; the `ui-context.md` scale (`rounded-2xl` cards, `rounded-3xl` modals) is applied at the call site via `className`, keeping foundation components untouched.

## Session Notes

- **Node IDs carry a per-client-session segment, and the collision it prevents was the common case rather than the rare one.** `createCanvasNodeId` is now `<shape>-<session>-<timestamp>-<counter>`. The earlier `<shape>-<timestamp>-<counter>` was documented as a remote risk; it was not. Every ID is minted in a browser, so two clients collide whenever their timestamps agree to the millisecond *and* their counters agree — and the counters agree by default, because both start at zero on load. Two people opening the same fresh room and each dropping their first shape is exactly that case, and the result is not a duplicate but a **silent overwrite**: `applyNodeChanges` reconciles an `add` onto an existing key, so one person's node replaces the other's. Verified by bundling the real module twice for two independent module states: 10 assertions, no collisions across 400 IDs, session segment stable within a client and distinct between them.
  - `crypto.getRandomValues` (6 bytes, 48 bits) rather than `crypto.randomUUID`, and the reason is not style: `randomUUID` is only defined in a **secure context**, so it is `undefined` over plain HTTP — a dev server opened at `http://192.168.x.x:3000` from a phone, say — and every node creation would throw. Nothing else in the app requires a secure context today (checked: neither the Liveblocks nor the Clerk browser bundles call it), so using it would have traded a collision for a hard failure. It is also the technique `createRoomSuffix` already uses, so the codebase mints random identifiers one way.
  - Generated lazily on first use rather than at module scope, so importing the module never runs the CSPRNG: a client component is pre-rendered on the server too, and a session id minted there would be discarded on hydration.
  - `12-shape-panel.md` item 6 was amended to match, and says so — the original requirement asked for shape + timestamp + counter, and the session segment is a later correction rather than something the spec had asked for.

- **`@liveblocks/react-flow` ignores `remove` changes.** `applyNodeChanges` and `applyEdgeChanges` both end in `case "remove": break` — nothing is deleted, and nothing is reported. So `onNodesChange([{ type: "remove", id }])` is a silent no-op, and **`onDelete` is the only way to delete from a room**. Read this before assuming the change appliers are symmetrical; four of the node change types are handled and one is not.
- **React Flow's `fitView` is a latch, not a read.** `useReactFlow().fitView()` sets `fitViewQueued: true` and pushes a no-op onto the node queue; the flag is only cleared by a `setNodes` or an `updateNodeInternals` where `nodesInitialized` is true — meaning every node has a `measured` width and height from the resize observer. So calling it immediately after adding nodes is correct and self-scheduling, and wrapping it in a `requestAnimationFrame` buys nothing. Related: `getFitViewNodes` filters on `measured` alone unless `includeHiddenNodes` is passed, which is the option that falls back to a node's declared `width` / `height`.
- **A 1px border plus `aspect-ratio` is not the ratio you asked for.** Tailwind's preflight sets `border-box` sizing, so `aspect-[2/1]` constrains the *border* box while percentage lengths and an `inset-0` `viewBox` resolve against the *content* box. A 1px border therefore turns a 288×144 frame into a 286×142 content box, whose ratio is 2.014 — and any percentage-positioned layout inside it is scaled by two different factors. `ring-1` (a box-shadow) instead of `border` keeps the two boxes identical. Same family as the percentage-padding and absolute-inset traps recorded above: the box a percentage resolves against is rarely the one you are looking at.
- **A component can be verified in a browser without the app *and* without hand-writing its markup.** `esbuild` and `react-dom/server` are both already in the tree: bundle a small entry that imports the real component and `renderToStaticMarkup`s it, run that in Node, and inline the output into the harness page next to the compiled CSS chunks. An entry file outside the repo needs `absWorkingDir`, `nodePaths`, and `alias: { "@": repoRoot }` on esbuild's JS API, or `react-dom/server` and the `@/` paths do not resolve. This is strictly better than reproducing class strings by hand, which is what the earlier harnesses did.
- **A Radix dialog renders *nothing* on the server** — `renderToStaticMarkup` of an open `Dialog` returns an empty string, because the content is portalled. To verify one, bundle for the browser (`platform: "browser"`, `format: "iife"`) and mount it with `react-dom/client` in the harness page. React and Radix alone are enough; no Next.js runtime is needed.
- **Chrome's `--headless --dump-dom` runs page scripts, which makes it a test runner.** Put the assertions in a `<script>` at the end of the harness page, write the results into an element, and read that element out of the dumped DOM. Two traps: the in-page script must be its own file read with `readFileSync` rather than interpolated into a JS template literal, because a template literal eats every backslash escape in it (`"\n"` becomes a literal newline and breaks the string; `/rgba?\(/` loses its escape and changes meaning) — and an open Radix dialog **adds `aria-hidden` to its siblings**, so a regex looking for `<pre id="results">` stops matching once the attribute lands. Match `<pre id="results"[^>]*>`.
- **Headless virtual time does not advance CSS animations, so Radix `Presence` never unmounts.** A closed dialog keeps its content in the DOM waiting for an `animationend` that will not come. Assert `data-state="closed"` rather than absence from the document.
- **Grepping built CSS for a class name has to account for CSS escaping.** Tailwind writes `sm:max-w-2xl` as `.sm\:max-w-2xl` and `aspect-[2/1]` as `.aspect-\[2\/1\]` — colons, brackets, *and* slashes are all backslash-escaped. A plain grep for the class as written in the JSX finds nothing and reads as "Tailwind did not emit it", which is the wrong conclusion. Related and reassuring: Tailwind's scanner does pick up a class held in a plain string constant (`const PREVIEW_ASPECT_CLASS = "aspect-[2/1]"`), so a class does not have to appear inside a `className` to be emitted.

- `getUserList({ emailAddress })` is documented as an exact filter for the list endpoint but as a case-insensitive *partial* match for the count endpoint. `lib/clerk-users.ts` does not depend on which: it maps returned users back through their own verified addresses, so either semantics gives the same result.
- `@liveblocks/node` was **not** installed despite `10-liveblocks-setup.md` saying all required packages were. `@liveblocks/client`, `@liveblocks/react`, `@liveblocks/react-flow`, `@liveblocks/react-ui`, and `@xyflow/react` were; the server SDK the auth route needs was missing and was added at `^3.24.0` to match the rest.
- `@typescript-eslint/no-empty-object-type` is an **error** here, and Liveblocks' own generated `liveblocks.config.ts` fails it — the generator emits `{}` for every unused slot. `Record<string, never>` satisfies both the lint rule and Liveblocks' generic constraints (`LsonObject`, `Json`, `BaseMetadata`); `object` does not.
- `Session.FULL_ACCESS` and `READ_ACCESS` are deprecated in `@liveblocks/node` 3.x. The replacements are the literal permission arrays `["*:write"]` and `["*:read"]`.
- `useLiveblocksFlow` does **not** need its storage key declared in `liveblocks.config.ts`. It manages its own subtree under the `"flow"` key (configurable via `storageKey`) through internal APIs, so `Storage: Record<string, never>` still typechecks and `RoomProvider`'s `initialStorage` stays optional — `RoomProviderProps` wraps it in `PartialUnless<S, …>`, which makes it optional exactly when the declared Storage has no required members.
- React Flow's data generics are constrained to `Record<string, unknown>`, which **interfaces cannot satisfy** (no implicit index signature — they are open to augmentation). Node and edge data must be declared with `type`, not `interface`. The error surfaces at `Node<T, "…">`, not at the declaration, so it reads as a bad type argument.
- `react-error-boundary` is not installed and was not added. `CanvasErrorBoundary` is the local equivalent. Anything else needing a boundary should reuse or generalize it rather than pulling the dependency in for one more fallback.
- `colorMode="dark"` on `ReactFlow` appends a `dark` class to the wrapper element, which activates the library's own `.react-flow.dark` variable block. That is 2 classes of specificity; overriding it from `globals.css` needs 3 (hence the extra `canvas-surface` class), because React Flow's stylesheet is imported from a component and ends up in a different CSS chunk — relative order is not guaranteed.
- `useLiveblocksFlow` exposes no `setNodes` or `addNodes`. Its result is `{ nodes, edges, onNodesChange, onEdgesChange, onConnect, onDelete, isLoading }` and nothing more, so **adding a node means dispatching a React Flow `add` change** — `onNodesChange([{ type: "add", item: node }])`. `applyNodeChanges` in `@liveblocks/react-flow` handles `add` and `replace` identically: it looks the ID up in the `LiveMap` and *reconciles onto the existing node* if one is there. So an `add` with an ID already in the room is an overwrite, not an insert — which is why node IDs carry a counter and not just a timestamp.
- **During `dragover` the browser withholds the dragged data; only `dataTransfer.types` is readable.** `getData()` returns `""` until the drop. Any decision about whether to accept a drag — `preventDefault()`, the `dropEffect` cursor — therefore has to be made from the MIME type alone, which is the argument for a custom type over `text/plain`.
- **Setting `width` / `height` on a node record sizes it.** React Flow v12 resolves the wrapper's inline size as `node.width ?? node.initialWidth ?? node.style?.width` (same for height), so explicit dimensions on the node are applied as styles and a renderer can just use `h-full w-full`. `initialWidth` / `initialHeight` are the SSR-only variants and are not what this needs.
- **`position: absolute; inset: 0` does not stretch an `<svg>` that has a `viewBox`.** This cost a real bug and was caught only by measuring in a browser. An SVG with a `viewBox` is a replaced element with an intrinsic aspect ratio, and CSS resolves `width: auto` / `height: auto` on an absolutely positioned replaced element from that ratio rather than from the insets — so `inset-0` on a 1:1 viewBox produced a **square** frame: 200×200 inside a 200×140 diamond, 180×180 inside a 180×90 hexagon, 160×160 inside a 160×100 cylinder, each hanging out of its node. The screenshot looked plausible, which is the point: the shapes were the right *shapes*, just the wrong box. `h-full w-full` alongside `inset-0` is load-bearing, not redundant, and there is a comment on the line saying so.
- **Tailwind only emits utilities it saw in the project's own source, which constrains any throwaway page that inlines the compiled CSS.** The verification harness first used `flex-col`, `gap-10`, and `flex-none` for its own layout; none appear in `app/` or `components/`, so none were in the emitted CSS, and the harness silently laid out wrong — flex items shrank and made a 216×216 circle render as an ellipse, which read as a component bug. Any page built from `.next/static/chunks/*.css` must style its own scaffolding with inline CSS and use utility classes only for the markup under test.
- **A percentage `padding-top` / `padding-bottom` resolves against the containing block's *width*, not its height.** So `py-[25%]` is not a vertical quarter of a non-square box. `top`/`bottom`/`inset-y` percentages do resolve against height, which is why the node label insets are `inset-*` utilities.
- **`setDragImage` needs an element that is already in the document and painted.** `display: none` and `visibility: hidden` disqualify it, and an element created inside the `dragstart` handler has not been laid out. Off-screen (`fixed`, far negative `left`) is the way to keep one available, and any future drag source needing a custom ghost should reuse the shape panel's pre-rendered layer pattern rather than building one on the fly.
- **WebKit will not start a native drag from a `<button draggable>`.** Long-standing behaviour, and the reason the shape panel's items are `div`s with `role="button"`. Any future drag source should be a `div` too.
- Liveblocks distinguishes retryable from non-retryable connection failures, and only the latter reach a React error boundary. A `500` from the auth endpoint is retried forever, so the suspense fallback stays up; `useErrorListener` is the only way to observe it. Worth knowing before assuming an error boundary covers "the room did not connect".
- **Canvas visuals can be verified in a browser without running the app, and this is now the pattern.** `/editor/[roomId]` needs Clerk, a project row, and a live Liveblocks room, which is why nothing there has been on screen. A presentational canvas component needs none of that: render its markup into a standalone page, inline the app's own compiled CSS chunks from `.next/static/chunks/*.css`, load it over `file://` in headless Chromium, then *measure* with `eval` rather than judging by eye. `13-node-shape.md` was verified this way and it found a bug a screenshot alone did not (see the SVG sizing note above). Two rules make it trustworthy: read the geometry out of the source files instead of retyping it, and assert that any class strings the harness reproduces still appear in the component — otherwise the page drifts and tests something the app no longer does. The harness lives in the session scratchpad, not in `scripts/`, since it is not repo tooling.
- The signed-in app has been opened in a browser at least as far as creating a project (see the corrected note above), but nothing from `08-editor-workspace-shell.md` onward has been looked at on screen **inside the app** — the node shapes were verified standalone, per the note above. The wiring was verified the same way the API was: pure helpers and the client request layer exercised directly (with `fetch` stubbed), the data helpers exercised against the real database, and the HTTP surface checked signed out. What remains unverified end to end is only the browser behaviour — the dialog opening, the navigation, and the refresh. The workspace shell inherits this: the access logic is proven against the database, but the navbar title, the sidebar highlight, the AI slide-over animation, and `AccessDenied` have not been looked at on screen.

- **An absolute inset resolves against the containing block's *padding* box, not its content box.** This cost a real bug and was caught only by measuring. The label editor was anchored `absolute inset-0` against the box `NodeShapeFrame` renders, and two of the six geometries pad that box (`px-3` on the rectangle, `px-5` on the pill) — so the editor came out 24px and 40px wider than the label it was replacing, and reached under the pill's curved end. Anchoring it against `NodeLabel`'s own `relative` box, which *is* the content box, took the read-vs-editing delta to 0px on centre-Y, width, and left for all six shapes. Same family as the percentage-padding trap recorded above: the box a percentage or an inset resolves against is rarely the one you are looking at.
- **A `<textarea>` cannot be vertically centred, so it has to be sized to its content and centred as a box.** Text in a textarea starts at the top regardless of `align-items` on anything above it. The label it stands in for is centred, so the editor is wrapped in a centring flex and the textarea's height is set to its own `scrollHeight` in a `useLayoutEffect` on every change. A plain `useEffect` flashes a one-row box for a frame; the layout effect runs before paint.
- **React Flow's CSS and the app's CSS are separate chunks, and their order is not fixed.** `@xyflow/react/dist/style.css` is imported from `collaborative-canvas.tsx` while `globals.css` is imported from the root layout, and Turbopack emits them as two files. Any override of a library rule has to win on specificity, never on source order — the existing `.react-flow.dark.canvas-surface` block already assumed this, and the resize-handle rules were verified by loading the two chunks in the *worse* order and confirming the handles still came out 7px, `#00c8d4`, ringed `#080809`.
- **React Flow's `--xy-*` seam does not cover everything.** `--xy-resize-background-color-default` themes a handle's fill, but its 5px box and `#fff` ring are literals in the library's stylesheet with no variable behind them. Restating those needs a rule, not a variable. Related: an early harness run measured the handle background as `transparent` — that was the harness missing the library chunk entirely, not a cascade problem, and is worth remembering as a failure mode of the inline-CSS verification pattern: a page that loads only *some* of the built chunks will silently measure unstyled elements.
- **React dispatches events from the root container, so `stopPropagation` on a synthetic event does stop a `document`-level listener.** That is what keeps `Backspace` inside a label editor from reaching React Flow's delete shortcut and removing the node. React Flow also guards its own key handling with `isInputDOMNode`, so this is belt and braces — but the belt is what makes `Escape` mean "close the editor" instead of "clear the selection".
- **`@liveblocks/react-flow` decides what syncs in `NODE_BASE_CONFIG`, and it is worth reading before assuming.** `selected`, `dragging`, `measured`, and `resizing` are all `false` there, meaning local-only — so a resize in progress does not broadcast intermediate geometry and only the committed `width` / `height` reach Storage. It also pauses history for the duration of a drag or a resize and resumes on release, so an undo steps over the whole gesture rather than every frame of it.

- **React Flow's resizer only puts grab handles on corners.** `XY_RESIZER_HANDLE_POSITIONS` is `['top-left','top-right','bottom-left','bottom-right']` and `XY_RESIZER_LINE_POSITIONS` is the four edges, drawn as 1px lines. Edge *midpoints* are therefore free, which is what let connection handles land there without a mode switch or a modifier. Worth checking before assuming a collision: an early verification harness invented eight resize dots and made the two sets look like they overlapped, when the real component never renders a handle at an edge midpoint at all.
- **`Handle` already carries `nodrag` and `nopan`.** Starting a connection cannot drag the node or pan the pane without any work on our side. It also carries state classes worth styling against: `connectingfrom`, `connectingto`, `valid`, and `connectionindicator` (which React Flow adds to every handle a connection could legally start from or end at).
- **`.react-flow__handle` is `pointer-events: none` at rest and `all` via `.connectionindicator`.** So hiding a handle with `opacity: 0` alone leaves it fully interactive — four invisible grab targets straddling every node's edge, half of them outside the node's own box, intercepting drags meant for the pane. Opacity and pointer-events have to be toggled together. Re-arming on hover is safe because a handle is a DOM child of `.react-flow__node`, so the pointer sitting on the outer half of a handle still counts as hovering the node and the reveal does not flicker off mid-gesture.
- **`defaultEdgeOptions` is merged into the connection *before* `onConnect` is called** (`{ ...defaultEdgeOptions, ...params }`), so it reaches `@liveblocks/react-flow`'s handler and is written into Storage. That makes it the wrong tool for a purely visual default — anything set there is persisted into every room's document.
- **React Flow's dark palette is not this app's dark palette, and edges are where that bites.** `--xy-edge-stroke-default` is `#3e3e3e` in its dark block, tuned for its own `#141414` canvas; on `--bg-base` (`#080809`) an edge drawn with it is effectively invisible. Any new React Flow element should be checked against the real background before being called done.
- **`NodeToolbar` is worth reading before positioning anything above a node.** It portals into `.react-flow__renderer` (not the pane, not the viewport), positions itself with `getNodeToolbarTransform` from the node's measured bounds and the live transform, and applies `offset` *outside* the viewport scale — so the gap is the same screen distance at every zoom while the node it belongs to is not. Its `isVisible` prop, when omitted, means "visible only when this node is the sole selection"; passing a boolean overrides that entirely. And it spreads unknown props onto its div, so `role` and `aria-label` pass straight through.
- **d3-zoom's `dblclick.zoom` deliberately bypasses React Flow's event filter**, by the comment in `XYPanZoom`: it is bound on the selection because a double tap on a touch screen circumvents the filter. So `nopan` and `nowheel` say nothing about double-click zoom, and anything mounted inside `.react-flow__renderer` — which includes every `NodeToolbar` — is exposed to it.
- **The browser harness can hover, which makes a `:hover` rule verifiable rather than merely readable.** `browse hover <selector>` fires a real pointer move, and reading the computed style immediately after catches the transition mid-flight (a 5px glow measured 2.08px); reading it again a beat later gives the settled value. Worth knowing for any future timed state: measure twice, and treat the first read as evidence the transition exists rather than as its endpoint. Selectors must also be unique — the harness rendered the same toolbar twice and `hover` refused to guess.

- **Positioned siblings with no `z-index` stack in document order, which decides what a node's controls paint over.** `NodeShapeFrame`'s root is positioned, so rendering it after the resizer put the resize controls under the node's own fill. Order inside a custom node is: shape, then resizer, then handles — the last one also wins the hit test where a handle crosses a resize line.

- **`useOthersMapped` compares each mapped entry shallowly, which is what makes a returned object literal safe.** `useOthers(selector, shallow)` would compare the *array* one level deep and see a new object per entry every time, so it never matches; `useOthersMapped` compares per connection. It is the difference between the avatar group re-rendering on every pointer move in the room and not re-rendering at all.
- **`ReactFlowProps extends Omit<HTMLAttributes<HTMLDivElement>, 'onError'>`, so `onMouseMove` on `<ReactFlow>` is the wrapper's DOM handler**, firing over nodes, edges, and empty canvas alike. React Flow's own `onPaneMouseMove` fires only over the pane, which for a cursor would mean the pointer vanishing whenever it rested on a node.
- **`useStore` and the rest of the React Flow hooks work outside `<ReactFlow>` as long as `ReactFlowProvider` is above them.** That is what lets the cursor layer read the live viewport transform from a sibling of the canvas rather than from a `Panel` inside it — and a sibling is what it has to be, because a `Panel`'s own `right: 0` is unlayered library CSS that a utility class does not win against.
- **The shadcn `Tabs` primitive states its active colours under `dark:` as well as bare, so overriding it takes both.** `data-active:bg-background` *and* `dark:data-active:bg-input/30` are in the trigger's own class list, and this app always has `dark` on `<html>`, so a bare `data-active:bg-*` override loses to the variant. `tailwind-merge` resolves the pair correctly once both are passed — modifiers are normalized, so the order they are written in does not matter.
- **The `Textarea` primitive already ships `field-sizing-content`.** Worth knowing before writing an auto-resize: bounding it with `min-h-*` / `max-h-*` is the whole implementation, and any ref-based sizing would be fighting a CSS property that is already on.
